# Accounts and connections: current state (Q-100 stage A/B input, D-190)

Architect, 2026-11-11. Read-only survey of `personal` at 3fdb1e6. Input for the Connected accounts hub and first-run setup design (next round, after the competitor brief and UI audit). ## 1. Summary

- **Five linked things, three storage places.** Secrets live only in Windows Credential Manager through `vault.py` (targets `jobscraper:<ats>:<host>` and `jobscraper:imap:<host>`, `vault.py:53-63`). Account facts live in SQLite (`ats_accounts`, `mail_accounts`, `settings`). Browser sessions live in an Edge user-data dir outside the repo (`config.py:104`). Ollama has no stored state at all.
- **Everything that is stored survives a restart.** That covers vault entries, account rows, mail cursors, the paused state and the Edge profile. Only in-process state resets: the mail timer's schedule (`web/mailsync.py:102-110`, the first check comes `startup_delay_s` = 60 s after start, `config/config.yaml:211`) and the Ollama probe cache (`backends.py:117,120-141`).
- **Only Gmail-for-status has a web UI** (MailCard, `web/src/tabs/Settings.vue:305-306`). ATS accounts, the apply mailbox and the Edge profile are CLI-only: `accounts list|add|export-edge` (`cli.py:1105-1209`), `mail set-password|test` (`cli.py:862-942`) and `apply open-profile` (`cli.py:1331-1344`). Model health is only in `doctor` (`cli.py:120-126`) and in failures after the fact.
- **Dead pointers.** Failure hints send the owner to "Settings → Accounts" and "Settings → Apply" (`apply/contracts.py:169,175,193`). Neither section exists: Settings has Cycle, Companies per run, Appearance and Email (`web/src/tabs/Settings.vue:202,246,280,305`). Both were planned for M21 (`docs/architecture/apply_design.md:1506-1514,1524-1525`) and never built.

## 4. Reuse, and new read-only endpoint shapes

**Reuse as is:** `GET /api/mail` for both Gmail rows and the application mailbox `ready` flag (`web/routers/mail.py:137-155`). All mail write routes stay MailCard's (`:169-273`); the hub links to them or embeds MailCard. `GET /api/applicant` `missing`/`completeness` (`web/routers/applicant.py:173-176`). `GET /api/profile` `present`. `GET /api/jobs/current` for "an apply run is using Edge" (`web/routers/jobs.py:84`). `store.accounts()` (`store.py:1623-1625`). `vault.get(...) is not None` as a boolean probe, already used by `_application_mailbox` (`web/routers/mail.py:103-106`). `backends.build(cfg.budget).available` / `unavailable_reason` (`backends.py:143-145`). `setupSteps()` (`web/src/setup.js:6`).

**New, read-only (shapes only; no secret, no password, no password length in any response; GET only):**

```
GET /api/connections            -> {checked_at, items: [ConnectionItem]}
  ConnectionItem = {kind: "gmail"|"apply_mailbox"|"ats_account"|"edge_profile"|"model"|"profile",
                    id: str, label: str, health: "ok"|"attention"|"off"|"unknown",
                    code: str|null, message: str|null, last_ok_at: str|null,
                    fix: {label: str, href: str|null, cli: str|null} | null}
GET /api/connections/ats        -> [{id, ats, tenant_host, email, status, has_password: bool,
                                     created_at, verified_at, last_signin_at, last_signin_ok,
                                     exported_to_edge_at}]
GET /api/connections/apply-mailbox -> {primary: {host, port, username: str|null, password_set: bool},
                                       backup: {separate: bool, host, username: str|null, password_set: bool}}
GET /api/connections/edge       -> {exists: bool, in_use: bool, sync: bool,
                                     mygreenhouse: "signed_in"|"signed_out"|"unknown"}   # "unknown" until G6's signal exists
GET /api/connections/model      -> {backend, model, local: bool, available: bool,
                                     code: "unreachable"|"model_missing"|null, checked_at}  # server-side cache ~30 s
```

`/api/connections` composes the others with existing views; it holds no logic of its own beyond mapping to `health`. The Edge `exists`/`in_use` values come from a filesystem stat and the job manager. Nothing launches Edge to probe it.

## 5. Constraints and ownership

- **Peer jobscraper-48 owns** `mailstatus/`, `mailstatus_flow.py`, MailCard's API and behaviour, and `apply/` account creation and credential handling (`apply_flow.py:1437-1548`, `vault.py` callers). The hub may display these and call existing APIs. Any new `apply/` or `mailstatus` API (G2, G4 password, G6 job kind, G7, G11, and any `apply/contracts.py` copy) needs that peer's sign-off through the outboxes.
- **Secrets never reach the browser** (NF-02, `docs/prd.md:224`). Password inputs follow the MailCard pattern: no `v-model`, read once, cleared before send (`web/src/components/MailCard.vue:11-14`). The server never echoes them (raw body parse, `web/routers/mail.py:8-11,59-79`), and they reach the vault only through a child process over stdin (`web/mailsync.py:254-259`).
- **Layering** (NF-04): SQL only in `store.py`; model calls only through `backends.py`; `web/` must not import `imapread` or `mailstatus_flow` (`web/routers/mail.py:3-6`).
- **No real account creation or submission in development.** The hub's tests use a stub vault (`keyring.set_keyring`, `vault.py:15-16`) and a DB copy; dev runs on 8768 with `JOBSCRAPER_MAIL_SYNC=0`.
- **No login**: one user (`instructions/01_scope_and_goals.md:11`), bound to loopback, guarded by Host and cross-site-write checks (`web/api.py:85-89,249-250`; `cli.py:281-284`).
- Writes stay where they are. In the first cut the hub is read-only plus links to existing actions. Any new write is a separate, peer-approved item.

## 6. Optional local app lock (recommendation only; out of scope per D-190)

Recommend **not building it now**. Everything a lock would guard can be read by any process in the owner's Windows session without the UI: Credential Manager entries (keyring), `data/applicant.yaml`, the DB and the Edge profile. The API is also open to any local process. A UI lock would therefore protect against a person at an unlocked PC, not against malware, and Windows' own lock (Win+L, Hello on resume) already covers that person. Windows Hello is technically possible: WebAuthn platform authenticators work on `localhost`, a secure context. But it would add a session cookie, an auth middleware on every route and a recovery path to a single-user app. If the owner wants a gate later, the cheapest useful form is a WebAuthn step-up only on credential and irreversible actions (store or replace a password, disconnect, switch `apply.mode` to auto), not a whole-app lock. That would need an owner decision, an ADR, and the KA-3 dossier.
