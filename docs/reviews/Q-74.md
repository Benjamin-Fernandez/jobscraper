## Findings

### F1 HIGH: tier 5 can now decide S answers and volunteer S values to employers (contradicts ADR-0008 Option C)
`apply/resolve.py:1196` (`corpus_text` with `sensitive=`), `:1420`, `:1446`; `applicant.py:1775`.
With the flag on, the S values go into the grounding corpus. So `grounded` accepts evidence and capitalised words that only S facts support. The `t2.sensitive` gate (`:1492`) protects only questions that a tier-1/2 rule recognises.
- Scenario (choice): a required custom Greenhouse question "Which ethnic group best describes you? (diversity report)" matches no tier-2 sensitive row, and its section is not `demographic`. The profile has `race: chinese`. The model picks "Chinese" with evidence "chinese", and the evidence is in the corpus. The answer is FILLED, and in auto mode it is submitted. Before D-105 the same reply got "evidence not found", went UNGROUNDED and was captured as a question. That is the model deciding a sensitive answer.
- Scenario (text): "Tell us about yourself" (or a required cover-letter field, `:1468`). The model writes "...a Singapore citizen, Buddhist, born 2001..." The words "citizen", "Buddhist" and "2001" now ground against the S lines, so the text fills and goes to the employer. Before D-105 these were `word ...` / `year ...` violations.
- `_shows_s_value` only tags the answer as sensitive. It still fills.
- llm_fill already handles this case: G2d (`int/Q-35-M guards.py:548` "private fact without a matching rule" -> unknown) and a G3 `facts_corpus` built from non-private facts only (`guards.py:427`, kept by design §4). Resolve tier 5 now behaves differently from llm_fill.
- Fix: with `ctx.model_sees_sensitive`, a tier-5 result whose value (or choice evidence) contains an S value from a protected path (`identity.date_of_birth`, `identity.gender`, `singapore_status.*` S leaves, `us_self_id`, `declarations`) becomes UNGROUNDED or UNKNOWN with `sensitive=True`. It is then captured as Private, and once the owner answers, tier 3 decides it by code. For text answers, add a violation "private value" (never the value) so the one retry can drop it. `contact.*` values may still fill, which matches the ADR's "contact details" benefit. Add pins for both scenarios. If the Architect prefers to keep the corpus wide, that needs an explicit ADR amendment, because it reverses Option C.

### F2 MEDIUM: tier-5 failure notes can now carry S fragments, stored unredacted and untagged
`resolve.py:1262` (`"evidence not found: " + ev[:60]`), the text violations `number N` / `year Y` / `month M` / `word W`, `_llm_failed` `:1343` (no `sensitive`).
- The docstring (`:1248-1249`, "never a profile value") held before only because the model never saw S values. Now the model often quotes the prompt's JSON form, e.g. `date_of_birth: 2001-03-12`. That quote is not a substring of the corpus, which holds values only, so the note stores the date of birth.
- The note goes to the audit row `note` (`apply_flow.py:303`, the DB, unredacted) and to `CapturedQuestion.note` (`questions.py:203`), both with `sensitive=False`. The job log stays safe: `_Log` scrubs `redaction_values`.
- Fix: when the flag is on, replace `applicant.sensitive_strings` hits in the note with `[private]` before building the Answer (in `_llm_failed`), or drop the quote from the "evidence not found" text.

### F3 MEDIUM: Ollama "cloud" model tags pass `is_local` (spec disagreement, spec wins for now)
`backends.py:236-251`. Ollama on 127.0.0.1 forwards models tagged `*-cloud` (e.g. `gpt-oss:120b-cloud`) to ollama.com. If `budget.ollama_model` is ever a cloud tag, S values leave the machine, while the badge says "Private: local AI only" and the doctor says "the local AI may read them". The owner's current tag is local, so this is not live.
- Fix (Architect amendment to §1): `is_local` also requires `not model_id.lower().endswith("cloud")` (covers `:cloud` and `-cloud`). Add a pin.

### F4 MEDIUM: `sensitive_strings` tagging is unreliable in both directions
`applicant.py:1805`; `resolve.py:1354`.
- Under-tagging: matching is verbatim and whole-word. The answer is not tagged when the option label differs from the stored slug ("pr" is under 3 characters, so "Permanent Resident" never matches; "Buddhist" vs "Buddhism"), when a date is written another way ("12 March 2001"), when a number answer gives the birth year, or for `+6591234567` against "91234567" (the lookbehind is a digit).
- Over-tagging: the leaves include generic values such as "decline", "yes" (`disability_status`), "citizen" and "+65", so ordinary "Yes" or "+65" answers get tagged Private.
- Logs are still safe, because `redaction_values` is a superset. The cost is in the audit's order and the Private tags. Most of this goes away if F1 is fixed with evidence-based detection.

### F5 MEDIUM: §4 llm_fill hook list (`comms/outbox/software-engineer.md`, Q-74 note) is incomplete
Checked against `int/Q-35-M` ae45cc7 `apply/`. Listed correctly: `facts.fact_catalogue` (351-376), `facts_text` (385-393), `pagefill.py:134` `run.sv`, `llm_fill.field_view` `_withhold` (268), and no `debug_dump` writer yet. Missing:
1. `llm_fill.recheck_entry` (612-625): calls `field_view` and redacts its prompt with `s_values`. It needs the same flag decision as the user prompt.
2. `llm_fill.pick_option` (569-576): the prompt and the `fmt` are redacted with `s_values`. Keep the redaction or not, but decide explicitly. Keep `pick_refused` as it is.
3. Fill cache: the key is `(job_id, field_sig, prompt_version, model, inputs_hash)` (`store.py:315`, `pagefill.py:649`). `inputs_hash` uses the *redacted* resume (`pagefill.py:138`), so flipping the flag does not invalidate the cache. ADR-0008 Consequences says "Prompt hashes change ... cached fills re-run once", which is false for this key. Design §4 also says the hashes "don't change", so the two documents contradict each other. Fix: fold the effective flag into `inputs_hash` (or `prompt_version`), and correct the ADR.
4. `guards.py:421-422`: the invariant "the model saw the redacted resume, so a quote can't carry an S value" breaks once the prompt is unredacted. Re-check G3 quote handling and update the comment.
5. `guards.py:691`: only `[private]` echoes are rejected. With the flag on, this is the llm_fill side of F1. G3's non-private `facts_corpus` covers it only while the resume contains no S value. Add a pin: flag on, a model-written text value with an S value that is not in the resume gives unknown.
