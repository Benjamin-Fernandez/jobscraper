What holds, checked by reading the code:
- **Sensitive data never reaches the model.** `extra` is not in `applicant.LLM_ALLOW`, so no saved answer reaches a tier-5 prompt, sensitive or not. Naming (`questions.ask_model`) returns before any call for a sensitive question. The naming prompt holds the employer's label, help text and options, plus the titles of non-sensitive `extra` keys only. It holds no profile value, no answer and no employer name. A tier-2 stop (a sensitive no-fit, or a D-75 conflict) still returns before tier 5 (`resolve.py:1463`). The model only names: `parse_naming` re-checks the key pattern and kind, and a `same_as` merge only opens a card. The new label is added to `extra.labels` only when the owner saves that card, which shows every label ("Also asked as").
- **Tier 3 matching** (`resolve._extra_answer`, `resolve.py:983`): an exact normalised label. Two entries with the label means no answer (`memory ambiguous`), and an entry that fails `extra_entry_errors` is skipped. A choice needs exactly one offered option whose norm is in `picks`, by equality and never by substring. A multi needs every offered option in `seen`. `by_employer` matches the exact `employer_norm` of the name or an alias, and an override that doesn't fit gives no answer (no fallback to the base). Employer-specific declarations are skipped in tier 3 and in capture. The order "tier 2 answer, then tier 3, then tier-2 stop" follows QD §6.2.
- **D-75 `country_bool`** (`resolve.py:895-939`): the value comes from the country, else `default`, else the standing answer. When the named countries disagree it stops (`work rights differ`), is not sensitive and never reaches the model. "without sponsorship" is `a and not s`. The loader refuses `country_bool` on other keys and refuses `value_map`/`yes_if` on it. `work_rights_text` is always added to grounding and to the tier-5 APPLICANT JSON.
- **The owner's file:** both writers hold `PROFILE_WRITE_LOCK`. A stale etag returns 409 `changed` and a YAML file that can't be parsed returns 409 `unreadable`. Validation errors return 422 with `[{path,message}]`. Nothing is written on 409 or 422. The write is atomic (tempfile in the same folder, then `os.replace`). The commented backup is made once, beside the profile, and its name matches the `data/applicant*.yaml` ignore rule. The path is always `cfg.applicant_path`. An answer endpoint only writes at a `target_path` that came from a captured row (a FORM path or a canonical path), never at a path from the client, and `set_path` refuses a type clash. Keys the form doesn't know round-trip unchanged.
- **Web API:** the routers are auto-mounted under `/api`. Binding is unchanged (`cli.py` 259-261). The existing Host/Origin guard (`web/api.py` :84-152) covers the new PUT and POSTs, and the JSON body models mean a cross-site `text/plain` POST can't forge an answer or a retry. Retry takes at most 20 jobs, each must be ready, `JobBusy` returns 409, and there is no `dry_run` flag, so the effective mode applies. Auto mode needs a confirmation in the UI, and apply_flow's duplicate rules are unchanged, so a retry can't cause a double submission.
- **Privacy (NF-01/02):** the new tables hold employer text only. `CapturedQuestion.note` is never persisted. Redaction still walks `extra` values, `picks` and `by_employer`, and skips only question metadata. There is no logging in the routers or the UI. `localStorage` holds only `profile.view`. The UI marks S fields "Private: never sent to the AI" as plain text, shows sensitive answered values as "•••", and masks S paths under "Other keys". The diff has no personal data: config and fixtures are synthetic.
- **Layering:** `applicant → apply.contracts` is allowed by D-73 rule 7. `questions.py` imports only its own stage and the foundation. The routers import foundation, `web.*` and `store.utcnow` only.
- **UI copy** matches QD §10.2, with two small deviations: the card's 409 `unreadable` text leaves out `(<error>)`, and the auto-mode retry toast is not in the spec. Neither needs a fix.

## Findings

### F1 HIGH (spec-sanctioned: does not block this merge; close before WP-Q1b): an answer to a generic label is reused on unrelated questions
`src/jobscraper/apply/resolve.py:983-1024` (`_extra_answer`: label-only match, runs for optional fields too); `src/jobscraper/apply/questions.py:489-493` (`assign_key` rule 3 groups every same-label question under one key).

- **Why:** tier 3 matches only the normalised label. Follow-up questions often share a generic label ("If yes, please specify", "Please specify", "If other, please specify", "Comments", "Please select"). The question they belong to is in the help text or the preceding field, and neither is part of the match. Rule 3 also puts every such question from every employer into one card. That card shows one label ("Also asked as" has nothing to list) and no context.
- **Failure scenario (probe, synthetic):** the owner answers Shopee's "If yes, please specify" after a relatives question with "My cousin works in the Shopee finance team". On a Grab form, an **optional** "If yes, please specify" whose help asks about certifications resolves `status=filled tier=3 src=memory:extra.yes_please_specify` with that text. In auto mode (D-77) Grab receives a wrong and private answer, and the owner was never shown the field.
- **Fix (architect to amend QD §5.2/§6.2; engineer + tester after):**
  - Add a generic-label guard in `questions.py`: a label with fewer than 2 content tokens after `STOP_WORDS`, or on a small `GENERIC_LABELS` list, is never matched at tier 3 by label alone.
  - Capture such a label with its context in `label_norm` (the label plus the normalised description, or plus the preceding field's label), so its sig and key are specific.
  - Tester: an oracle with two generic-label fields with different help text, asserting no reuse.
  - D-78 makes this more pressing: a model filling forms generically also needs the preceding question as context.

### F2 MEDIUM: a profile-gap answer can be lost on the next "Save details"
`web/src/components/ApplicationDetails.vue:86-110` (`reloadKeepingEdits`).

- **Why:** after a card saves, the form takes the new etag but keeps a whole top-level section from the local draft if that section was edited locally.
- **Failure scenario:** the owner has unsaved edits in Contact. They answer a profile-gap card whose target is `contact.address_line1`. The draft keeps the old `contact` without the answer and gets the new etag. "Save details" then PUTs with a matching etag, and the server overwrites the answer it just saved. The group stays `answered`, so the job shows as ready, the retry fails again and the question is captured again. It fails closed, but the owner's answer disappears without a message.
- **Fix:**
  - Merge at leaf level: apply only the leaves the owner changed relative to `before` onto `next`, or write the saved value into the draft at `target_path` after a profile-gap save.
  - `removeAnswer` (:204) also saves every other unsaved edit without saying so. Mention that in the confirm text or save only the removal.
  - Add a vitest.

### F3 MEDIUM: one variant's answer marks the whole group answered; a variant's old pick can't be cleared
`src/jobscraper/web/routers/questions.py:236` → `store.py:1686` (`set_questions_status` by key); `web/src/components/QuestionCard.vue:107,123`; `questions.py:148`.

- **Why:** the card accepts a pick for any one variant and drops the empty ones, but the server marks every row of the key `answered`. An answer scoped to one employer also marks the other employers' rows `answered`. A variant the owner empties in "Change answer" is not sent, so its old pick stays in `picks`.
- **Failure scenario:** jobs that saw an unanswered variant, or another employer, show "can go again". In auto mode the owner confirms "Send n applications now?". Each retry then stops on the same question and the question is captured again: wasted attempts and a misleading banner, though nothing wrong is submitted. A stale pick stays active for its option set after the owner thinks they removed it.
- **Fix:**
  - For choice and multi, mark `answered` only the rows (question ids) that received a pick. For a scoped answer, mark only the rows whose sightings are from that employer.
  - Send `[]` for a variant that was cleared, and have `_merge_picks` drop that variant's norms.
  - Tester: oracles for both cases.

### F4 MEDIUM: an all-caps "US" label falls to the job's country, contrary to D-76
`src/jobscraper/apply/resolve.py:135`.

- **Why:** D-76 says a bare all-caps `US` in the verbatim label means the United States. The code adds `and any(ch.islower() for ch in label)`, so in a label written entirely in capitals it is read as the pronoun, and the country falls back to `job_country` (SG).
- **Failure scenario:** today it does no harm, because the defaults are equal everywhere. Once the owner sets `US: false` (or `requires_sponsorship.US: true`), "ARE YOU AUTHORIZED TO WORK IN THE US?" is answered with SG's value. The probe returned `['SG']`.
- **Fix (spec wins):** follow D-76 and treat it as US. If the architect wants the pronoun case covered, add both US and the job country, so a difference becomes the `conflict` stop and is never a silent guess.

### F5 MEDIUM: D-75 is not live yet; work-rights questions still reach the model
`config/questions.yaml:33-104` (unchanged in this diff).

- **Why:** the four old `bool` rows (`authorised_to_work.SG/.US`, `requires_sponsorship.SG/.US`) are still there, and there is no `country_bool` row (WP-A04, researcher). `_tier2_country_bool` is never selected at runtime.
- **Failure scenario:** right-to-work questions for other countries fall through to tier 5. So do SG questions when the owner's map has only `default:`, because `REQUIRED_PATHS` no longer asks for `.SG`. QD §1/§8.2 say these "never fall through to the model". The model is told the standing answer and is grounded, so this isn't unsafe, but it isn't D-75 either.
- **Fix:** land WP-A04 (two `country_bool` rows, `exclude: [without]` on sponsorship) before the M20 gate, with an end-to-end oracle through `load_rules(config/questions.yaml)`.

### F6 MEDIUM: GET pairs a profile and an etag from two different reads
`src/jobscraper/web/routers/applicant.py:87,93`.

- **Why:** `load(path)` and `etag(path)` read the file separately.
- **Failure scenario:** a hand edit or CLI write lands between the two reads. The form gets the old profile with the new etag, and its next PUT overwrites the edit without a 409. The window is small.
- **Fix:** read the bytes once, and parse and hash those same bytes (`applicant.load_with_etag`).

### F7 MEDIUM: the whole-file PUT keeps no previous version
`src/jobscraper/applicant.py:325-339`; `web/routers/applicant.py` `put_applicant`.

- **Why:** missing fields are not validation errors. A PUT of a partial profile, for example from a UI bug, is valid and replaces the file. The commented backup is made only once.
- **Failure scenario:** after the first save the owner has no copy, and the data is gone (NF-01: the file is gitignored, so git has no copy either).
- **Fix:** before each web save, copy the current file to `data/applicant.prev.yaml`, one rolling copy (it matches the ignore rule). Tester: extend the nf01 backup-path oracle.
