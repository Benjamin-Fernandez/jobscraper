### MEDIUM

**F2. Keep on an "Answered for you" row can overwrite the owner's real answer and reach other questions.** `apply_flow.py:721-731` (`_naming_wanted`) lets the naming model run for an assumed, non-sensitive question with no profile target; `apply/questions.py:718-721` (`parse_naming`) lets the model's `same_as` join any listed key of the same kind; `assign_key` (`questions.py:793-797`) then gives the assumed question that existing key. Keep saves the sent (assumed) value to `extra` under that key (`kept_value`, `questions.py:477-503`), so the AI's guess replaces the owner's real standing answer and `extra` feeds P3 and the briefing for every label the key lists. Scenario: the owner answered "willing to relocate: No" earlier; a form asks "Can you relocate to <city>?", the model assumes Yes and names it `same_as: willing_to_relocate`; the owner clicks Keep. The same naming also costs up to `naming_max_per_attempt` (10) model calls of up to 20 s each per page, inside the fill loop (`apply_flow.py:758-763`), against a 420 s attempt budget. **Smallest fix:** `_naming_wanted` returns False when `q.reason is QuestionReason.ASSUMED` (rules 2, 3 and 5 of `assign_key` then apply: exact label or a fresh slug; a Keep can no longer land on another question's key).

**F3. An `open` question is silently demoted to `assumed` (departure 7), and an assumed sighting rewrites its `reason`.** `store.py:2132` turns `open` into `assumed`; the UPDATE two lines later also overwrites `reason` with `assumed`. The design (§6.3) names only `answered` -> `assumed` and says nothing else changes. Scenario: the owner has an open `profile_gap` question (an `owner_fact_missing` stop for a numeric field); another form with the same signature is answered by the AI with an assumed value; the row becomes `assumed`, leaves the Questions "open" list, and `retry_candidates` (`store.py:2307`, `HAVING ... reason != 'assumed'`) stops listing the stopped role as "ready to retry". **Smallest fix:** an `open` row stays `open` and keeps its `reason` when an assumed sighting arrives (add the sighting only); only `answered` becomes `assumed`.

**F4. The owner cannot see what an `AlwaysStop` attempt nearly did, and the copy for a content failure misleads (departure 11).** `always_stop` (`apply_flow.py:1525-1543`) raises before `stage()` runs, so that page has no audit rows and no captured questions; for `unanswerable_required` the Applications text is `REASON_TEXTS` (`contracts.py:189-191`): "A required question had no answer JobScraper could back up: “would be guesses: application”. Answer it under Profile -> Application details, then retry." Nothing is captured, so there is nothing to answer; the queue banner (FILL_FAILED) says the same. The `retry_candidates` change (departure 12) correctly keeps such a role out of "ready to retry". Safe (nothing is sent), but the first live content failure will send the owner hunting. **Fix:** web copy for a detail that starts with a content-failure marker ("The filler would have had to guess on <step>. Nothing was sent. Fill this role by hand or skip it."); better, let the stop carry the page's decided answers so `stage(applied=False)` can record them (always.py owner).

**F5. A failed "Add another" no longer stops a required section (rev L7 as specified; note the disagreement with D-174).** `apply_flow.py:1678-1681` clears `added` under `always`, and `bad` (line 1683) skips rows with an entry problem, so a form with 1 of 2 education entries proceeds to the scan and Submit. The spec wins (§4.5 "a note, not a stop"); but the only trace is a job-log line and a `fill_failed` audit row, not the Applications pill. **Fix:** none required; list it as an accepted risk in the go-live record and surface "1 of 2 education entries added" in the attempt summary (U1).

**F6. Pre-existing, outside the diff, but S1 makes it bite: `declarations.prior_employment` matches a one-word employer name against the first word of a longer past employer.** `declarations.py:63-69`. The engineer's observation is right and wider than "Example": with invented names, a one-word employer matched a past employer `<word> Tree Pte Ltd`, and three other one-word names behaved the same way. Under S1 a confident reader's value is written and the model's disagreement is only a note (§4.2), so a false "I have worked here before: Yes" (or "currently employed here") goes onto a real form in the owner's name. Strict writes the same value today, so this is not a regression; it is a wrong-declaration risk to close or accept before the policy widens the number of forms filled. **Fix:** require a full normalised-name match or an alias for a one-word employer (tester pin, declarations owner); until then check the owner's past employers against the watchlist names (checklist).

### LOW

**F7. K1 registration order and coverage.** `resume()` (`apply_flow.py:918-945`, called at 1167) runs the tailor's model call before any secret is registered; `forbid_known_secrets` (1322) runs after `detect`, `resolve_ctx` and `precheck`, and covers this tenant's account rows plus the profile mailboxes' IMAP passwords, not every vault entry (the mail-status mailboxes, `mailstatus_flow.py:239`, are the same vault service only when they share the application mailbox). The tailor prompt holds the master resume and the JD, so no real exposure; moving the registration to the top of `attempt()` would close it. Also: lower-casing in `forbid_known_secrets` (`m.lower() in rows`) can miss a vault entry stored under a different case; the sign-in path registers it again with the exact key (1999).

**F8. `BriefingRefused` hides which key.** `apply_flow.py:1373-1375` logs "a profile key looks like a secret" without the key path, though the exception message names it (names only, no value). One stray `extra` key such as `..._password` (slug of an answered "password hint" question) fails EVERY attempt with `error` "prompt check" until the third pauses the queue (`REPEATED_ERRORS`). Fail-closed and correct, but undiagnosable. **Fix:** log `str(exc)`; add the check to `doctor`.

**F9. `config.py` edge values.** `_max_entries` (`config.py:160`) catches `TypeError`/`ValueError` only: `max_entries: {education: .inf}` raises `OverflowError` at start-up (config.yaml only; `llm_fill` is not a settings key, so the Settings table cannot reach it). `always_trial_runs: 3.0` or `true` in YAML reads as 0 (trial off) with a warning; a whole-valued float should be accepted. Non-numeric `llm_fill` ints raise `ValueError` in `_coerce`, as every config key already does. None of these can switch the policy on or lift a cap: `fill_policy` and `always_trial_runs` are normalised and never raise (probe: 'ALWAYS ' -> always; `True`, `1`, lists, dicts, 'alwayss' -> strict).

**F10. Import-time `RuntimeError` on constant drift.** `apply_flow.py:2475-2476` raises at import if `apply/always.py`'s copy of `CONTENT_FAILURE_DETAILS` differs. Correct to fail closed, but it would take the whole apply module (and the web app that imports it) down at start-up. A test pin gives the same protection without the outage.

**F11. `at.always` is set on the pre-D-78 path.** `apply_flow.py:1085` sets it from the policy alone; `body()` (1172) takes the rules path for a non-navigator adapter even with `fill: llm`, where `resolve_ctx` (995-998) would hand the rules resolver `model_sees_sensitive=True`. Unreachable today (Greenhouse and Workday are both navigators), reachable by a test fake. **Fix:** `at.always = policy is ALWAYS and _is_navigator(adapter)` after `detect`.

**F12. `is_content_failure` ignores the reason code** (`apply_flow.py:2491-2497`). A `document_missing` detail is the employer's file-slot label (`always.py:2266`); one that began with a marker would pause the queue `fill_failed`. Require `reason_code == unanswerable_required`.

**F13. Fallback count can double.** `always_page_done` (1689) adds a page's F2-F6 answers on every `page_result`, including the second fill of the same page (after Next errors, and the pre-Submit refill), so `last_resort_max_attempt` can trip early. Fail-closed (a `fill_failed` pause), never a submit.

**F14. Smaller items.** (a) The F3 last-resort `pick_call` swallows `PromptRefused` (`always.py` ~1988-1990), so the attempt does not end "prompt check" there as §2 K1 says; nothing is sent either way (B2). (b) Trial: the counter never resets when the owner raises N, and the log line at `apply_flow.py:1089` reads `always_trial_used()` outside the `try` (an unreadable settings table fails the attempt before it starts, fail-closed). (c) `compose_assumed` and `compose_files` are reset only in `begin_item` (queue); a batch `apply` run can carry a stale "assumed" mark to the next job's composed text (over-flagging only). (d) `NEUTRAL_TEXT` duplicates the tailor's wording (departure 10). (e) Two processes opening a v6 DB at the same instant can both try the ALTER (`duplicate column name`); the same pattern already exists for every earlier column.

## The eight questions

**1. Secrets (K1).** *Registered before any prompt, on every path?* The briefing prefix is first sent at the warm-up (`apply_flow.py:1384-1398`, `warm(..., messages=)` which runs `_guard` first, `backends.py:353`). Before that, `forbid_known_secrets` (1322-1349, called at the body_llm step just before `always_services`) registers this tenant's vault passwords and the profile mailboxes' IMAP passwords; failures reading the vault are skipped and re-read at the point of use. Generated passwords are registered the moment they exist (`sign_up`, 2029, inside the `while True` so a regenerated password is registered too); a vault password read for sign-in at 1999; the IMAP password when mail loads (`forbid_mail_password`, 2126, called from `wait_for_mail` 2098-2105, including the post-Submit security-code read, where a registration failure ends `submitted_unconfirmed`, not `failed`). Page calls and compose go through the same backend instance (`_RefusalWatch` wraps it, `services.backend`; `tailor_flow.compose(backend=self.backend)`), so they are checked by the same `_guard` (`backends.py:161-175`: raw, JSON-escaped both ways, percent-encoded, whitespace-stripped). The queue's second and later items: `clear_secrets()` in `attempt()`'s `finally` (1122) and a fresh registration per attempt. *Gaps:* the tailor prompt runs before registration (F7, LOW); a secret nobody registered cannot be caught (pasted into `extra`; `check_no_secrets` only refuses secret-named keys, F8). *Refused prompt retried with less checking, or its text kept?* No. `PromptRefused` carries no text (`backends.py:174-175`), nothing is retried without the check (`pagefill` turns it into `transport_failed`; the flow maps it to `error` "prompt check", 1650-1653; compose maps `transport: PromptRefused` likewise, 1795-1797), and the log line is a fixed string. A too-short secret (< 6 characters) aborts the attempt under `always` (`forbid`, 1304-1320) and is logged and ignored under strict.

**2. Submission safety.** *Submit without a passing scan:* no. `submit` (1512) is reached only after `pre_submit_scan` returns; under `always` a hit gets one `refill` round and a rescan, still a hit -> `validation_error` (1589-1607); a scan that cannot run stops an auto attempt in both branches (1583-1588, 1596-1602). Every `AlwaysStop` ends in `always_stop`, which always raises (1525-1543), so the `except` at 1505 cannot fall through to Submit. *Twice / one in flight:* `submit`, `claim_click`, `apply_duplicate` and the queue worker are untouched (diff has no hunk in them); `retry_candidates` only lists, the owner's click re-queues, and `apply_duplicate` still guards a role that was ever submitted. *Trial:* `choose_policy` returns True only when the policy is `always`, `self.dry_run` is False and `used < N` (1285-1302); it then sets `mode, dry_run = "dry_run", True` (1075-1076) before the attempt row's mode is written and before `context()` reads `dry_run` (1056); nothing in the diff ever sets it to `auto`; `finally` restores the base values, which the queue overwrites per item via `set_mode` (2223). A dry-run attempt is never counted (line 1294) and never raised. An unreadable counter counts as a trial. *Counter race:* the read is at attempt start and the increment at the review page, in one worker under `RunLock` and one `run_queue` loop, so there is no concurrent reader; the read-modify-write in `count_always_trial` (`store.py:1923-1928`) is not atomic, which is irrelevant with a single writer. Nothing the Settings API exposes writes `apply.always_trial_used`.

**3. Policy gate.** `effective_policy` (`apply_flow.py:549-559`): `always` only if `fill_policy_value(...) == "always"` AND `acfg.fill == "llm"` AND `backends.is_local(backend)`; probe (read-only, constructed `OllamaBackend` objects): 127.0.0.1 and localhost -> always; a LAN IP, a hostname, a `...-cloud` or `:cloud` tag, a userinfo URL trick and `OffBackend` -> strict; `fill: rules` -> strict for all; 'bogus' -> strict. Always-only branches and their guards: `_Attempt.counts` and `assumed_count` (`self.always`); `audit_row` writes `assumed` (0 under strict); `resolve_ctx` extra (`self.policy is ALWAYS`); `choose_policy` trial (policy ALWAYS); `forbid_known_secrets`/`always_services`/warm messages (`at.always`, 1433); `_RefusalWatch` use in `page_result` (`at.always`); refill (`at.always`, 1498-1503); `always_page_done` (`at.always`, 1671); E5 note (`added and at.always`); compose forcing and kwargs (`forced = at.always and f.required`, `kw` only `if at.always`); `forbid_mail_password` (`policy is ALWAYS`); `except AL.AlwaysStop` (only `always.py` raises it); `pause_for`'s owner-fact clause (only `owner_fact_missing` rows); `questions.capture_assumptions`/`capture_owner_fact` (called only from the always branches); `upsert_question` assumed branch (only reason `assumed`); `retry_candidates`' extra reason and HAVING (strict never writes `assumed` reasons). *Changes under strict* (the engineer lists secrets only; the full list): (1) `forbid` at sign-in and sign-up registers the password under strict too (a strict prompt that held it would now be refused and end `model_unavailable`; a random generated password, or a vault password of 6+ characters, will not appear in a form label or JD, so harmless in practice); (2) `clear_secrets()` after every attempt; (3) compose `PromptRefused` -> `error` "prompt check" (departure 9); (4) `choose_policy` logs "apply: fill_policy always ignored..." only when configured `always`; (5) `audit_row` carries `assumed: False`; (6) the loop and review sit inside a `try` (indentation only); (7) the module imports `always`/`briefing` and checks the marker copy (F10); (8) doctor prints one extra line. None changes a decision, a stop or a submission. `-k apply_flow` 148/148 and the engineer's strict probe agree.

**4. Stops (§9).** `owner_fact_missing`: question captured (sensitive; `profile_gap` + path, else `no_rule`), attempt `failed`, not returned (`RETURNS_ITEM` unchanged, `contracts.py:268`), queue continues; the clause at `apply_flow.py:2545-2551` pauses `repeated_failures` only for 3 in a row with the SAME fact (lower-cased) and returns None for mixed facts, so it never joins the generic streak. `document_missing`: nothing captured; per role; the generic 3-same-reason streak still applies, as the design says. `model_unavailable`: transport only, returned (unchanged), a refusal is excluded (1650).
