## Verdict

**READY WITH CHANGES.** The split is the right one: the model names the class, code holds the truth, and code writes over the model only when both agree. A wrong class on one side can only veto or flag. That removes the H1 failure (an ordinary question rewritten from `consents.*`) and the "one detector, two jobs" cause behind H2/H3. I would not send it back for another design round. But §17.1 has **three holes that let a false statement through** and **one that would stop most real forms**. All four have a paste-able fix below; the rest are MEDIUM/LOW and also fold in without a round.

The two-key table is sound for the *class* decision. It is not yet sound for the *value* decision, because everything it does (override, veto, "H", the confirm call) rests on code's polarity readers and on `asked_classes`, and I found wordings where those readers are confidently wrong or too wide.

## Required changes (numbered; HIGH blocks building as written)

### C1 HIGH. A confident-but-wrong polarity reader makes cell "both keys right" write a false statement; the checkbox "tick if" rows are undefined; "unusable confirm" writes the model's value (§17.1 rows 1 and 3; §17.4 L1)

Evidence (probes, `_as_asked(pf, truth=False, statement=True)`, i.e. the answer the owner's "does not apply" truth takes; the owner is not bankrupt, not a PEP, has no record):

| Wording | Right answer | Reader says | Both keys (model `declaration:*` and code finds the class) writes |
|---|---|---|---|
| Is it untrue that you have never been bankrupt? | No | **Yes** | Yes (admits bankruptcy) |
| Is it false that you have no criminal record? | No | **Yes** | Yes |
| Do you deny that you are a politically exposed person? | Yes | **No** | No (claims PEP) |
| Would it be incorrect to say you have been convicted of an offence? | Yes | **No** | No |
| Tick if you are a politically exposed person (CHECKBOX) | untick | **None** (`attestation_polarity` None; "tick if" / "check this box if" lead is not handled) | undefined in §17.1 |
| Check this box if you have been convicted of a criminal offence | untick | None | undefined |

`untrue`, `false`, `deny`, `incorrect` are not in `declarations.NEGATIONS`, so the reader is *confident* (n=1) and wrong; §17.4 L1 lists only "prevent / stop you / free of / unable to / fail to" (and "free of" already reads correctly). Row 1 ("Both") says "write T's option", so the override writes the reader's mapping over a model that may be right. The two checkbox rows are the code review's H2 rows 1 and 2: both keys name the class (classify finds `pep` and `criminal_record`), but T's option cannot be computed because polarity is None; §17.1 says nothing for that cell, and pin (5) "untick" cannot pass with the readers as built. Finally row 3 ends "`""` → the model's value, assumed 'check: <class>'": for a model-named `declaration:*` where H is unknown and the confirm call is unusable, that writes whatever the model said, which is exactly the adverse value the table exists to stop.

Counter-example for question 2 (wording that breaks the H-unknown row): *Es-tu une personne politiquement exposée ?* with options Oui / Non; model class `declaration:pep`, value "Oui". Code key silent (classes empty), H unknown, `option_stance("Oui")` unreadable. The confirm call is the same 14B model at temperature 0 with the same reading difficulty; if it returns "" (or an option outside the list) the row writes "Oui". For a declaration "assumed" is not enough: the owner reads the flag after the form is submitted.

**Amendment (paste into §17.1):**
1. After the table: "*H is unknown* also when the wording holds an implicit negator (untrue, false that, not true, deny, denies, incorrect, wrong that, prevent, stop you, free of, unable to, fail to) or when `attestation_polarity` / `_as_asked` returns None. When H is unknown the reader never overrides, **even when both keys name the class**: the field takes the confirm row."
2. "*A checkbox* whose label classifies as a declaration, holds no negation word and has no attestation lead ('tick if', 'check this box if', 'select if', 'tick this box if') is read as: ticked = the declaration applies (H = ticked). With a negation word and polarity None, H is unknown."
3. Replace the last clause of the "H unknown" row: "`""` → the class's **protective end**, except for `consent_*`, `certification`, `acknowledgement` whose T is *agree* or unset (there the model's value, assumed)." So a `declaration:*`, `work_right`, `sponsorship`, `self_id`, `owner_fact`, `other_person` value that code cannot read and the confirm call cannot settle is never written.
4. Add `untrue`, `false that`, `deny`, `incorrect`, `wrong that` to `declarations.NEGATIONS` handling as "implicit negator → reader tentative" (declarations owner; `strict` benefits too, byte-for-byte unchanged for every wording that has none of these words).
5. Pin: the six rows above, model correct and model wrong, class `declaration:*` and class `ordinary`.

### C2 HIGH. `owner_fact:address|postal_code|phone` keyed on `asked_classes` fires on fields that are not those facts; veto + F1/stop then ends most forms (§17.2 owner_fact row, §17.5 M1)

`asked_classes` (always.py:972) is a word match on the label: probe results on the current code: *Email address* and *Confirm email address* (EMAIL) → `address`; *Home page URL*, *Home country*, *IP address*, *Address Line 2*, *Street* → `address`; *Phone Device Type* (dropdown), *Country Phone Code* (dropdown), *Phone Extension*, *Do you have a mobile phone?* (radio), *Referee phone number* → `phone`. §17.2 makes that the code key of an owner fact whose H is "a value that differs from the profile value after normalisation" and whose end is F1 (copy the profile value) else `owner_fact_missing`. Failure scenario: a Workday "My Information" step: *Phone Device Type* = "Mobile" (correct) differs from the profile phone → vetoed → A5 → F1 copies a phone number into a dropdown, which cannot hold it → `owner_fact_missing: phone` with the text "This form asks for your phone, which isn't in your profile or resume" while the phone IS in the profile. The same for *Country Phone Code* "Singapore (+65)" and for a non-locked *Email address* field. Also "normalisation": the profile keeps `contact.phone_number` and `contact.phone_country_code` apart and address as `address_line1` / `address_line2`, so a model value "+65 9000 0000", "9000 0000" or "Line 1, Line 2" would "differ" under equality.

**Amendment (replace the code-key cell of the owner_fact row for address / postal code / phone):** "*Narrowed:* only on a TEXT, TEXTAREA or PHONE field whose label names the value itself (address, address line 1 or 2, street address, postal code, postcode, zip, phone / mobile / telephone number) and holds none of: email, e-mail, url, website, web, home page, ip, country, city, state, code, type, device, extension, ext, 'do you', 'have you', 'are you'; never a choice list, checkbox or other-person field. *Compare by containment:* a phone matches when the digits of the profile number (without the country code) occur in the value's digits or the reverse; an address value matches when it is made only of `address_line1`, `address_line2` or their join (case-insensitive, punctuation dropped); a postal code on equal digits." Pin the nine labels above (no veto, model value kept) next to the three real fields.

Related (MEDIUM, same section): `address_line1`, `postal_code` and `identity.date_of_birth` are only RECOMMENDED in `applicant.RECOMMENDED_PATHS`. If the owner's real profile lacks them, every form that requires them ends `owner_fact_missing` (reasonable, but only after the first live form). Add one line to §17.8 and to `doctor`: print, as booleans, whether these three are set. See residual R9.

### C3 MEDIUM-HIGH. `declaration:other` has no code key, so an unclassed adverse yes/no with model class `ordinary` is written (§17.2, §17.5 M5)

Probe (`classify_all`): *Have you ever been dismissed or asked to resign from any employment?*, *Any pending litigation or legal proceedings against you?*, *Have you ever been refused a visa or denied entry to a country?*, *Are you currently under investigation by any regulator?* all give `classes=[]`. In §17.2 the `other` row's key is "the gated reader", which finds nothing, so the only key is the model's. A model that labels such a question `ordinary` (the rule-12 example covers "dismissed" but not the others) and answers Yes is the "Neither" row: written. §17.5 M5(a) therefore resolves the review's M5 only when the model cooperates. The code review's M5(a) fix (a generic adverse guard in `decide`) was dropped.

**Amendment (§17.2, declaration row):** "*Code key for `other`:* a Yes/No, checkbox or statement field whose label holds a frame (have you ever, are you currently, were you, has any, do you have any pending) with an adverse noun (dismissed, fired, terminated, sacked, asked to resign, litigation, lawsuit, sued, legal proceedings, investigation, inquiry, refused, denied, revoked, suspended, disqualified, convicted, charged, arrested, bankrupt, insolvent, misconduct, disciplinary). T = 'none applies' when every declaration class is false (D-87). Add the same to the briefing's D1 line ('no dismissal, litigation, visa refusal or investigation')." Then both-keys and one-key rows work for it like any class.

### C4 MEDIUM. Contradicting keys and `which` mismatches are undefined (§17.1)

The "Both" row needs the same class; "everything else must match exactly". Nothing says what happens when the keys name *different* protected classes or the same family with a different `which`. Examples: model `owner_fact:salary_current`, code `salary_expected` (label "Expected salary", a common 14B slip) → with equality failing, each key vetoes on its own H, T for current salary is empty, and the stop fires on an ordinary field; model `declaration:restrictive_agreements` on "Are you willing to sign an NDA?" (code reads `nda_willingness`, an ordinary class by D9) → code is silent for `declaration`, the model's key alone vetoes a "Yes" (willing) as H, the confirm call is primed with T "no restrictive agreement" and writes **No** to "willing to sign an NDA" (owner's `willing_to_sign_nda: true`).

**Amendment (§17.1, after the table):** "*Contradiction.* When code finds a class and the model names another: T comes from **code's** class; an override is not allowed; each key may veto only a value in its own H; if code positively names an ordinary class (`nda_willingness`, the D9 willingness classes) the model's protected class is dropped (its value stands, assumed, 'check: class'). For `owner_fact` and `self_id` a `which` mismatch counts as one key each with code's `which` used for T."

### C5 MEDIUM. A field that matches two consent frames (§17.1/§17.2)

"I agree to the Privacy Policy and to receive marketing communications" (and "...and to keep my details for future roles") is a very common single, often required, checkbox. Both frames fire; T differs (`privacy_consent` true, `talent_pool_opt_in` No / retention refused). The table does not say which wins, and D2 says marketing is "never a stop", so the likely outcome is an unticked required box and a late generic `validation_error` that blames the site.

**Amendment:** "A field matching more than one consent frame takes the **strictest** T. Required and refused → `consent_refused` with the refused part in the detail (add the detail 'receiving marketing messages' to the three in §17.6); optional → unticked. Also state `acknowledgement`'s key (suggest: it follows `certify_true`, unset → agree)."

### C6 MEDIUM. `self_id`: the H definition stops common forms; coverage words (§17.2 self_id row)

(a) H = "any option that is neither T's option (R0/R1 under §17.4) nor a decline". With T "Male" and options Man / Woman / Non-binary, or T "Single" and "Single (never married)", the M3 rule excludes the match, so a *correct* model pick is in H, the confirm call (WANTED = T) picks "Man", which is *also* in H by the same definition, and a required list ends empty → `validation_error`. (b) With T = `decline` and a required Male/Female/Other list, the end is "empty for the site" plus "never Other": defensible, but it ends as a plain `validation_error` the owner cannot act on, and must not reuse `owner_fact_missing` (its text says the fact "isn't in your profile"). (c) `_SELF_ID` lacks hispanic, latino, "ethnic origin" (has "ethnic"), "identify as", caste.

**Amendment:** "For a choice list, an option the `TASK_CONFIRM` call picks for WANTED = T counts as T's option (assumed); H is only what neither the model's pick, R0/R1 nor that confirm pick matches and is not a decline. A required self-ID list with no truthful option ends `validation_error` with the detail 'no <gender|race|...> option matches your profile (decline) on <step>'. Add hispanic, latino, latinx, 'ethnic origin', 'identify as', caste to the self-ID words. List `ordinary` **last** in `FIELD_CLASS_CHOICES` and in rule 12 (the protective classes are read first; a constrained decoder with a long enum leans to the first entry)."

### C7 MEDIUM. M3 is half symmetric (§17.4 M3)

The rule requires every token of the *option* to occur in the *wanted* value. A negation in the *wanted* value that the option lacks is not caught: wanted "Not Hispanic or Latino" against an option set that lacks it but has "Hispanic or Latino": option tokens {hispanic, latino} ⊂ wanted, coverage 2 of 3 = 0.67 ≥ 0.6, so R1 picks the opposite. **Amendment:** "...and every negation or contrast token of the wanted value (no, not, non, never, without, none, but, except, only, other, another, longer) occurs in the option."

### C8 MEDIUM. Content-failure copy still sits under the "Needs your answers" pill; `consent_refused` wiring list (§17.6)

`applications.attempt_view` keeps `unanswerable_required` in `_NEEDS_INPUT`, so a content failure shows the pill "Needs your answers" and a "Try again" next to the new text "Apply by hand, or skip this role" (flow F4's concern is fixed in text only). **Amendment:** "A detail that starts with a `CONTENT_FAILURE_MARKERS` entry is `kind: stopped`, not `needs_input`." For `consent_refused` the list in §17.6 is right but `apply_flow.pause_decision` (apply_flow.py:2637) has the same-detail rule only for `_OWNER_FACT`: three `consent_refused` endings with different details would fall to the generic branch and pause `repeated_failures "consent refused"`. **Amendment:** "`consent_refused` joins the owner-fact branch of the streak rule (same detail ×3 pauses naming it; different details return None)." Pin both.

### C9 LOW. Word lists (§17.4 H3/M8)

Add to `owner_fact`: "how old" (age), "social security", "ssn", "tax id", "tax number", "driver licence number", "employee id". Probe: `fact_of` returns '' for all of them today, and "How old are you?" does not contain "age".

## Answers to the ten questions

**1. Soundness of the two-key table.** Per family, with the cells of the question:

| Family | (a) both right | (b) model class wrong | (c) code key wrong | (d) both wrong, same direction | (e) class missing |
|---|---|---|---|---|---|
| consent_* | override to T; sound. A required refused box → `consent_refused`; unset privacy / certification / acknowledgement → agree, assumed (D5). Combined boxes: C5 | code key vetoes agree-when-T-refuses; sound for the frame list; value not in H passes (fine, T agrees) | code frame on an ordinary question with T refusing: the model's correct Yes is vetoed, then A5, then the confirm call writes T's "No" to an ordinary question (e.g. "Do you keep your CV up to date?" matches keep + your CV). Wrong answer, not an adverse statement; narrow frames make it rare | model reads an ordinary question as a consent and the frame also fires: T written (agree). The admitted residual, plus "both" | code key only: veto; never override. Sound |
| declaration | override; **not sound** where the reader is confidently wrong or checkbox polarity is None (C1) | code veto; sound where the reader reads; H unknown → confirm (C1.3 closes the "" case) | code reader on a tangential question: rare; the veto + confirm can write T's "No" | both name a declaration for a non-declaration question: writes "No" (the owner's declared truth, so not adverse) | veto only; sound |
| work_right / sponsorship | override from rows; sound for country rows. Unknown place or region: H should be "claims a right / no need", which `_as_asked` can read; spell that out | veto of a claim; sound. Weak for non-English labels | L4 reader on "relocate to Singapore": no | rare | veto only |
| owner_fact | F0/F1 profile value; sound | the code key vetoes unverified DOB / ID / grade / salary words; sound for the listed words | **C2: address / phone code key fires on non-facts** | n/a | veto only |
| self_id | T option written; sound, but C6 | veto of any non-T non-decline; C6(c) word gaps | n/a | n/a | veto only |
| other_person | veto of the applicant's own details | veto | n/a | n/a | veto only |

Where a false statement *is* submitted, besides the admitted residual: **(i)** C1 rows (reader confidently wrong, both keys right); **(ii)** C1 row 3 (H unknown + unusable confirm → the model's adverse value); **(iii)** an unclassed adverse yes/no with model class `ordinary` (C3), and any non-English adverse yes/no with model `ordinary` (no code key at all; residual R2); **(iv)** a confirm call that is wrong the same way as the first call (R3, correlated; unavoidable with one model). Of these only (iv) is inherent; (i)-(iii) are closed by C1/C3. "Assumed" is enough for the admitted residual: the model answers an ordinary question; the damage equals any other wrong ordinary answer, only biased toward Yes by D5. It is **not** enough for an adverse declaration (C1.3).

**2. H unknown.** Not acceptable for `declaration:*` as written; see C1 item 3 and the French PEP example. Protective end for any model-named class whose harmful direction exists; model's value assumed only for agree-by-default consents.

**4. The always-answer promise.** New ways a required field ends empty or an attempt stops: (1) `consent_refused`. Note `CONSENTS_MUST_BE_YES = (privacy_consent, certify_true)` in `applicant.py:1246` and `missing_for_apply` already refuse to start an attempt when either is false, so in the real flow `consent_refused` is reachable for **retention** (and the combined box, C5) only; the privacy / certification pin tests an unreachable-in-production path (fine as a unit pin; say so). (2) `owner_fact_missing` for address, postal code, phone: reasonable if the fields are real (C2), plus DOB / grade as before; address and postal code and DOB are only recommended, so a thin profile stops every Workday form once. (3) Required self-ID list with no decline and T = decline: empty, `validation_error` (C6). (4) Required marketing list with no refusing option: empty → `validation_error`, not a `consent_refused` stop; correct to avoid a false opt-in; C5 gives the combined box a proper reason. (5) Content failure: unchanged from earlier rounds; the new per-page cap is the only addition. (6) A required work-rights list for an unknown region: empty only if the model *claims* a right; a "No" is written. Too eager: C2 (stops on Workday phone-type / country-code fields and email) and C6(a) (a correct "Man" is vetoed). Not too eager: the others.

**5. The 14B model.** 41 strings as a per-field enum is realistic for grammar-constrained output; the alternation is prefix-shared (`declaration:` / `owner_fact:` / `self_id:`). The per-field `ref` enum already makes the schema much larger than the class enum adds, so no new risk class; the rehearsal already measures time per page, and should print grammar-compile time of the first call. Class first, value second is the right order (it is the only chain-of-thought available with thinking off). Weaknesses: (a) primacy bias, so put `ordinary` last (C6); (b) the second level (`which`) is where a 14B drifts; harmless for `declaration:*` (all agree), harmful for `owner_fact` / `self_id` (C4 makes code's `which` win); (c) rule 12 misreads: "worked / employed / applied here before" under `declaration` sits next to willingness (NDA, relocate, travel) which is ordinary; add a third negative example: "Are you willing to sign an NDA?" and "Are you willing to relocate?" are ordinary. "I certify the above is accurate" vs "Can you confirm you have 2 years of Python" is a good pair. The two negative examples are not enough for the three ordinary-vs-protected confusions that are likely in practice: willingness, "do you have a relative who can refer you" (relatives vs referral), "experience with <marketing/privacy topic>". Token and latency numbers in §17.3: +~200 tokens a 30-field page is plausible (a long enum value like `declaration:criminal_record` is more than 6 tokens; average 8-10 is realistic) and the 420 s attempt budget absorbs it; `TOKENS_PER_FIELD` 70 → 80 covers it. Chunking is unaffected (field-count based); `max_tokens_for` stays below the 8000 cap for 20 fields. A cut reply now loses a class too: a field without a class is "silent", which the table handles.

**6. Injection (M2).** The fence plus "class from the question only" is enough for the *leak* direction (page text cannot make code write a value; both keys are required to override and code's key cannot be forged by the model). For the *turn-off* direction (model labels a PEP question `ordinary`) the code key alone vetoes: confirmed from the table for the classes whose code key is a real reader (declaration with a found class, work_right with a country, owner_fact words, consent frames, marketing frame, self_id words). Classes whose code key is too weak to carry it alone: **`declaration:other`** (no key at all, C3); **non-English labels for every class** (every key is an English word list; protective only through the model's class); **`other_person`** (words and the preceding-field rule; and a P2-locked field never reaches the model, so the model's class cannot help); `self_id` words missing hispanic / latino. The reverse attack (page text pushes `owner_fact:*` onto an ordinary field) can only cause a veto and one A5 re-read, then a stop: a denial of one role, not a leak.

**7. Contract v8.** Additive: `CONTRACT_VERSION` 8; `-k apply_contracts` 72/72, layering 13/13; `test_apply_contracts.py:196` (`set(REASON_TEXTS) == set(ReasonCode)`) holds because the text was added with the code; `test_q76_d2_every_reason_code_has_a_kind_text_and_hint` accepts `consent_refused` as `stopped` until A1-W adds it to `_NEEDS_INPUT` (then `needs_input`, also in the allowed set). `web/src/attempts.js` parses only the `owner_fact_missing` sentence (`missingFact`); `consent_refused` falls to the label "Needs your answers" (kind-based), nothing breaks; the pill could say "Needs your agreement: ..." but that is optional. Texts read truthfully: "This form needs you to agree to the processing of your personal data, and your profile says no. Nothing was sent." is true for the reachable case (retention: "keeping your details on file for future roles"); for `certify`, "agree to a statement that your answers are true and complete" is awkward but accurate; the hint's "Profile → Consents" matches the form group `consents`. `CONTENT_FAILURE_TEXT` is truthful; its kind is wrong (C8). `ModelDecision.klass` / `.which` defaults make every existing constructor valid; `FIELD_CLASS_CHOICES` is derived, so a new `DeclarationLabel` changes the enum and the cache key together (fine, but pin the count 41 and the order so a drift is visible). One wording problem: markers are matched on the detail's *start*; a pre-A1 stored detail ("too many answers would be guesses on X") does not match. No live rows exist (policy off); no action.

Concerns: A1-A is one lane in a 2,700-line file with ~15 changes; run it as sequential commits with the tester's red pins first (A1-T before A1-A), and let the tester's pins land per row group, not one file. Also keep `apply.mode: dry_run` for the rehearsal (the plan says so).

**10. Anything simpler.** No simplification I would stake the review on. The nearest candidate (code never overrides; any disagreement or H goes through one T-primed confirm call) would remove the override row and so the "confidently wrong reader" cell, at the price of a call per disagreement and the confirm model's correlated errors; I prefer C1's narrower fix. One real simplification: rows 2 and 3 of the table can be one row ("a value in H or an unknown H → A5 once, then one confirm, then the protective end") since the outcomes are the same.

## Residual risks to record (accepted)

- **R1** An ordinary question read as a consent *and* answered Yes: written, assumed (D5 bias). Same harm as any wrong ordinary answer.
- **R2** Non-English forms: every code key is an English word list; protection rests on the model's class and the confirm call. Singapore careers sites are almost all English; record, and treat a mostly non-ASCII/non-English page as a candidate for the trial mode.
- **R3** The confirm call and the first call are the same 14B at temperature 0; a wording that fools one often fools both. The H-unknown path writes the confirm's option, assumed.
- **R4** A model-correct answer vetoed by a false-positive code frame, with T refusing, becomes T's "No" (wrong, not adverse). Rare with the narrowed frames.
- **R5** P2/P3-locked fields skip the model, so its `other_person` class cannot protect them; only the section / preceding-field words do.
- **R6** Both keys wrong in the same direction on a declaration writes the owner's declared truth ("No") to a question that is not a declaration. Not adverse.
- **R7** A late-stage `validation_error` is the end for several protective cases (required marketing list, required self-ID with no option): fail-closed, not an applied form.
- **R8** `consent_refused` for privacy / certification is unreachable in the real flow (`profile_incomplete` stops first). Keep the code (cheap) but do not count it as covered by a live trial.
- **R9** The first live run reveals which recommended fields (address, postal code, date of birth) the profile lacks; expect one `owner_fact_missing` per employer form until they are set.
- **R10** The model's class is cached in the decision; a stale cache row from a prior prompt version is a miss (`always:v2`), but a retry within a version replays the same class; a changed wording of the same field gets a new key.

## What I checked and found sound

- The core idea: override needs two independent keys, a single key can only veto, a veto always goes to a protective end. For every protected class the veto path holds with the model's class forced to `ordinary`, wherever the code key reads the label (declaration with a class, work rights with a country, owner-fact words, consent / marketing frames, self-ID words).
- Frames as the narrowing for H1: none of the seven H1 rows matches; the two required lists are not consent-shaped (`option_stance` cannot read Software / Data / Both).
- Mechanics need only the code key (P1-P3, F0/F1, G12, G13): this keeps strict-style fills working with a missing class.
- `klass is None` is silent, never override: safe default for fakes, cut replies and old cache rows; cache miss on `always:v2`.
- Contract v8: purely additive, derived `FIELD_CLASS_CHOICES`, `REASON_TEXTS` completeness test passes, no Vue parser change needed, `-k layering` 13/13 (contracts import nothing new).
- The JD fence, JSON-encoded QUESTION and the generic-label help rule (M2) close the code review's three injection routes; page text cannot make code write a value.
- The prompt budget: rule 12 adds ~450 tokens to the cached prefix; output +~200 tokens a page; no change to chunking; `max_calls_page` and the early content failure fix M6.
- Build plan files do not overlap; the work packages' verify commands separate the Edge-dependent tests (`-k apply_e2e`, `-k apply_flow`) as the handover requires.
