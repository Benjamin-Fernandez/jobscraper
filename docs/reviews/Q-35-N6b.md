## What holds

Auto mode = `not dry_run`; `dry_run = bool(args.dry_run) or acfg.mode != "auto"` is set once in `_Run.__init__` (N6a review, unchanged).
- *Every exception path fails closed in auto.* `scope`/`scan_required` raising (a page that cannot be evaluated: `read_page` raises by contract, `page.py:674`) -> `VALIDATION_ERROR` "review: could not check the required fields" (`:1218-1222`, `from None`, type name only in the log). A dry run says so and goes on (it sends nothing). `page_text` swallows errors and returns `""`, so a failed text read makes the resume check fail ("resume not shown") rather than pass. A hit -> `VALIDATION_ERROR` with the site's labels (`_labels_of` is best-effort, falls back to keys). `JobCancelled` (BaseException) is not caught by the scan. After the raise, `attempt()` takes the existing `fail` path (`at.clicked` is False), the page is closed, rows are recorded.

The guards before `body` (`cap_refusal` when not dry run) are untouched. (There is no oracle for this on the llm path: see F1.)
- *No sensitive value in the "not shown" line.* `:1241-1243` logs only `unseen` (an int) and a fixed phrase. The comparison reads `a.value` but never logs or stores it. The scan failure text carries site labels only (`x[:80]`, first 3, capped at 200), no field values.

## Findings

### F1 MEDIUM: the fail-closed and cap paths of the new auto-Submit route have no oracle
`tests/test_apply_flow_n6b.py` (`_scan` only fakes a return value, never a raise); `apply_flow.py:1216-1222` (`REVIEW_SCAN_FAILED`), `:1228` (resume check), `:1195-1201`.
- *Failure scenario (regression, not a present bug):* a later edit (for instance a "scan failures are not fatal" tidy-up of `pre_submit_scan`, or moving the try/except) makes `scan_required` raising fall through; the next auto-mode run on a page the scanner cannot read presses Submit with no check, and nothing in the suite fails. Same for the daily cap: `test_f4_the_flow_rechecks_the_caps_just_before_the_click` runs the old rules path with a fake adapter; no test shows the llm path (`body_llm` -> `submit` -> `claim_click`) refusing at `daily_cap`. This is the first code that can really submit through the new filler, so its negative paths are the safety net.
- *Fix (tester, ~3 tests, fixtures only):* (a) `scan_required` raising in auto -> `FAILED`/`validation_error`, detail `REVIEW_SCAN_FAILED`, `submit` absent, `submit_clicked_at` None; in dry run -> `READY_TO_SUBMIT`; (b) auto with `daily_cap` already reached by another click after the guards -> `CAP_REACHED`, no `submit` event; (c) a required text value not on the review page: the log line contains the count and none of the values.

### F2 LOW: no `check_page` between the last Next and the pre-Submit scan
`apply_flow.py:1192-1196`. The loop runs `check_page` before `next_step`, but the page that `next_step` lands on (Workday's review page) is never classified before Submit; the old rules path had the same gap, so this is not a regression, but auto-submit makes it matter. *Scenario:* a bot-check or CAPTCHA interstitial replaces the review page. Today it is stopped only indirectly: `submit_ready` finds no Submit button, and for an uploaded resume the name check fails ("resume not shown"). Both fail closed, with a misleading reason. *Fix (one line, raise-only, not evasion):* `self.check_page(page, at)` before `self.pre_submit_scan(...)`, so the stop is `captcha`/`bot_check` with the right reason and the owner sees why.

### F3 LOW: an optional `unknown` is replayed and never re-evaluated when the profile later gains the fact
`pagefill.py:660-684`, `:687-722`. An optional unknown cites no fact (`ref: ""`), so its `facts_used_hash` is constant; `inputs_hash` covers only resume + JD (+ the Q-74 switch). *Scenario:* attempt 1 leaves optional "GitHub URL" blank (the profile had no link, model says unknown); the owner fills `links.github` in Profile; the retry of the same job replays "unknown" and leaves it blank, for up to 30 days. The harm is a blank optional field, never a wrong value, hence LOW, and it is the cost of not re-asking every optional unknown on each retry. *Options:* accept (recommended), or also skip optional unknowns where `profile gap` is the note. Either way §13.3 should say what the code does (request to the architect). Not a disagreement with the spec: §13.3 says "latest fresh decision per field" and is silent on unknown; the Coordinator ruled the narrowing (D-169).

### F4 LOW: the review text check may be stricter than a real Workday review page, and short names are weak
`apply_flow.py:1226-1229`. The check needs the uploaded file name on the page. The local wd_a fixture prints it; I could not verify a live Workday tenant (no real site opened). *Scenario:* a tenant whose review page lists "Resume/CV" without the file name makes every auto Workday attempt stop "review: resume not shown": safe, but it would show up at the M20 gate as a false stop. The reverse weakness: a very short stem such as `cv.pdf` could match unrelated text, and the check proves only that a file of that name is shown, not that it is the right content. Both are spec-level (D-169 rules the substring); the dry-run audit read at the gate (D-83) is where to look. No change requested.

### F5 LOW (spec note, not N6b scope): G12's "minus the applicant's own employers" is applied only to composed texts
`apply/facts.py:247-268`. Design §7 G12 reads "minus the applicant's own employers from profile experience and resume entries (D-84 R1)" for the whole guard; the merged code removes them only when `composed=True`. Now that `rctx.other_employers` is filled (N6b), a `keep`/`extra` text that names an employer the applicant used to work for, when that employer is also on the watchlist or in a sighting, becomes `unknown` and is captured. Fail closed (a question card, not a wrong answer). The spec wins: raise it with the architect/lane M, not a blocker here.
