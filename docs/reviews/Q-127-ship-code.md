## 1. The lock: holds

### HIGH

### MEDIUM

**M1. Under strict, the Remember route never finds the attempt's captured question, so "Ready to try again" can never turn on for a no_rule stop, and the sensitive flag and the qualified label are lost.**
Trigger: any strict `unanswerable_required` stop (the live attempt's 18 `no_rule` fields), owner clicks "Answer for next time", then looks for the "Ready to try again" mark.
Effect: the audit rows are keyed by the AUDIT key (`<step>:<site id>`, apply_flow.py:1895-1899 via `page.audit_keys`, page.py:892-929) but the capture writes its sightings with the READER key (`f<n>_<token>`, page.py:288; `capture_page` `field_key=f.key`, questions.py:389; `add_sighting(... q.field_key ...)`, apply_flow.py:851). `store.attempt_field_question(attempt_id, row["field_key"])` (store.py, the JOIN on `s.field_key = ?`) therefore returns None; probe: `audit_keys` mapped `f3_ab12 -> my_information:weekend_q`. Consequences: `mark_answer_corrected` marks 0 question rows answered (store.py `mark_answer_corrected`), so `retry_candidates` keeps those rows open and `ready_to_retry_jobs` never lists the role; the entry is written with `sensitive: false` even when the captured row was sensitive; the label saved is the plain one, not the qualified one. "Try again" stays offered on every stopped row (`canRetry`), so the loop still works by hand; stops that name a profile path (`profile_gap` rows, joined by attempt id, not by key) do show ready. The unit tests seed equal keys (tests/test_q127_store.py:219), so none pins the real mapping. (The always path remaps explicitly, `always_page_done`, apply_flow.py:1846-1870; strict does not.)
Fix: in `_capture_questions`/`page_result`, pass the audit key to the capture for strict as `always_page_done` does (`akeys = self.stage(...)` is already returned at apply_flow.py:1822; rebuild `pfs` with `dataclasses.replace(pf.field, key=akeys.get(...))` before `self.capture(...)`), or make `attempt_field_question` match on label_norm + step as a fallback. Add one e2e pin (strict stop -> Remember -> `retry_candidates` open == 0).

**M2. A generic-label field (the live attempt's "unlabelled" fields) is a dead end: refused as too general, and if M1 were fixed the saved answer would still never be used.**
Trigger: a stopped field whose label is "Please specify", "Details", empty, or one word.
Effect: today (M1 present) the route answers 422 `too_general` ("Change it in your details instead") and there is no details field for it, so the owner can only apply by hand or skip: a regression against the old cards, which saved such answers per employer via `by_employer`. If the key mismatch is fixed, the captured label is the QUALIFIED one ("please specify | @step2#2"); `remember.is_generic` runs on that whole string (remember.py:102-109) and calls it NOT generic (probe: web `is_generic` False, `plan.is_generic` False), so the entry is written with `employer: ...` but tier 3 refuses generic labels unless the entry's `by_employer` names this employer (resolve.py `_extra_answer`: "generic label, not answered at this employer"; probe returned `None` with that note). The owner would see "Saved", then "Try again" would stop on the same field again.
Fix: in `remember.py` test generic on the part before " | " (as resolve.py does) and, for a qualified generic label, write `by_employer: {<employer>: {value|picks|seen}}` (the shape tier 3 reads) instead of `employer:`; or keep refusing and say plainly in the row copy "This question can't be saved; apply by hand or skip".

**M3. A "Your / My / Applicant's ..." label is never read as another person's field, which can fill the applicant's own contact into a Referee / Emergency block (strict path, #1).**
Trigger: a referee or emergency-contact section whose field is labelled "Your email address" / "My phone" and is an email or phone type.
Effect: `personal` refused the applicant's own details there (section words made it other-person); now L2 types the applicant's account email, and G2b / the R4 guard no longer stop the model from using the contact facts. By its label the field IS the applicant's, so this is the design's intent (fix2 C), but it is a strict-path loosening that was designed for the always filler and rides in on the shared `facts.py`.
Probe (the `personal` facts.py loaded beside this one): `about_other_person` for "Your email address" (email type) in "Referee details": personal True, branch False; "My phone number" in "Emergency contact": True / False; a plain "Email" there and "Referee email": True / True on both.
Fix: either accept (note in the release notes) or gate the lead-word rule on `rctx.fill_policy is ALWAYS` (one condition at facts.py:667) so strict keeps today's refusal.

**M4 (conditional, rollback only).** After first use of Remember with the default scope, rolling the code back makes "Only {employer}" answers global (section 4). Not a ship blocker; it is a condition for the rollback instructions.

### LOW
- L1. `update` of an entry that is this label's own replaces its value AND scope (remember.py:168-177, 438-447): remembering "8 weeks, only Employer B" over a global "4 weeks" removes the global answer, so other employers stop on that label again (fail-closed).
