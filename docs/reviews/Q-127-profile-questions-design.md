# Review: Q-127 design, no per-company questions on the Profile page (D-215)

**Reviewer**, 2026-11-15. **Reviewed:** `docs/architecture/q127_profile_questions_design.md` (Part A, B.1-B.10) and `adr/0012-no-per-company-questions.md` at `cd72792`, against the code in this worktree (= `int/Q-121`, schema v8) and `personal` @ 9c3982e. The architect's hand-over in `comms/outbox/architect.md` was read as a claim and checked. Nothing was run that starts an apply job; no `data/`, no `.env`. Skills `design:design-critique` and `design:accessibility-review` were not run as separate passes; the points that come from them are in §6.

## Verdict: READY WITH CHANGES

The diagnosis is right and the central move (R1: the Profile page never shows a question; the application view holds what was sent; a per-meaning counter, over employers, proposes at most one nameless field) meets D-215 and is the simplest thing that does. Three defects would let it do harm once built (H1 to H3): each is a short text change, none needs a second design round. Six MEDIUM changes tighten the D-215 literalness and the counter. The build order I would stake the review on is the Coordinator's single go-live from `int/Q-121`, with five conditions (§9).

## Required changes (paste-ready)

### HIGH (block the build until the text is changed)

**H1. A topic you Add must not carry the merged wordings as exact labels (B.1 R6, R4 last sentence, pin 12).**
Evidence: R6 saves `labels: every label_norm of the topic, up to 100`. Tier 3 and the lock L6 (`apply/resolve.py:1095-1135` `_extra_answer`, called from `apply/locks.py:301-304`) answer any field whose exact label is in an entry's `labels`, with a kind-only fit, and L6 is final: `apply/always.py:5698-5700` (`prefill`) returns `memory:` answers as the field's final state, with no model check. R4 says "A wrong merge or split only moves a counter; it never changes an answer". That stops being true at Add. Failure scenario: T4 merges "Notice period" (a number of days) with "When can you start?" (a date) into one topic of kind `text`; the owner adds it once and types "1 month"; from then on every employer's "When can you start?" gets "1 month" typed as its answer, silently, in a real submission (D-203).
Change: replace the R6 Add sentence's `labels: every label_norm of the topic, up to 100` with `labels: []` and add: "A promoted entry carries no labels. It reaches forms through the briefing (LFF §3: the model reads the entry's title, description and value next to the question's own wording, and the basis check of `always.py` verifies the `extra:<key>` basis); it is never an exact-label answer." Amend R4's last line to: "A wrong merge or split only moves a counter and a proposal's wording; an added field never answers a label by itself." Pin (12): an added topic's entry has `labels == []`, and a resolve of one of its wordings does not return `memory:`.

**H2. "Use a different answer next time" must never write to a key it did not create (B.2b key rule, B.8 pin 2).**
Evidence: B.2b says "the key is the attempt's captured row key for that field if one exists, else `slug_key(label_norm)`; never the model's `same_as`". The captured row's key can itself be model-named: under `strict`, `_capture_questions` calls the naming model (`apply_flow.py:795-816`, `assign_key` rule 4, `apply/questions.py:811-815`), and even an `assumed` row inherits a stored row's key through `assign_key` rule 3 (`questions.py:806-810`: "a stored row with this label and kind"). The writer then does `entry = extra.get(body.key)`, adds the label to that entry's `labels` and overwrites `target["value"]` (`web/routers/questions.py:432-474`, `_apply_answer`). Failure scenario (the flow review's F2 again): row A "Preferred work arrangement" was merged by the model into key `work_mode`; the owner corrects it on an application; the correction overwrites the owner's old `work_mode` answer and from now on answers every label of `work_mode`.
Change: in B.2b replace the key sentence with: "The key is always `slug_key(label_norm)` over the profile's `extra` keys, never a `questions` row's key. If `extra[key]` exists and its `labels` already hold this exact `label_norm`, update that entry (by scope). If it exists without this label, take the next free suffix (`_2`). The entry's `labels` is exactly `[label_norm]`. The write refuses (409) when it would change an entry that is `promoted` or whose `labels` has other wordings." Pin (2): a captured row with `named_by = model` and a key that already holds another entry: the other entry is byte-identical afterwards.

**H3. The remember route must not be offered, and must refuse, on answers that follow the owner's declarations (B.2b, B.5 `remember`).**
Evidence: `lock_field` runs L6 (`resolve.extra_answer`) before `_declaration_lock` (`apply/locks.py:301-320`), and `_extra_answer` only refuses `EMPLOYER_SPECIFIC_DECLARATIONS` (`resolve.py:1100-1102`). A held work-rights or locked-consent row that is FILLED wins first (`locks.py:297-299`), so those are safe by code order; the standing declarations (criminal record, bankruptcy, non-compete, NDA, D-87 all-No) are not. The design shows the button on every row, with scope "Every application that asks this" and no class rule. Failure scenario: the owner clicks it on "Have you been convicted ...?" to repair a wrong assumed Yes on one form, picks the first scope option, and a stored "Yes" now answers every declaration reading of that label at every employer, overriding D-87 and the profile.
Change: add to B.2b: "`can_remember` is false, and the route answers 422 `follows_your_details`, when the row's source is `profile:*`, `field_map*`, `standing:*`, `default:*`, or strict `declaration`, or when the row's class is `declaration:*`, `consent_*`, `marketing`, `work_right`, `sponsorship`, `self_id:*`, `owner_fact:*`. The row then shows 'This answer follows your details. Change it in Your details.' with a link to the section." Allowed: strict `attestation_unclear`, `no_rule`, `no_option_fits` and assumed ordinary rows. Default scope = "Only applications to {employer}"; "Every application that asks this" is the second radio and is never preselected. Pin (13, new): remember on each protected source/class is refused and writes nothing.

### MEDIUM (change before the build; each is small)

**M1. Proposals must not show a verbatim wording (R6, B.4 proposed field).** A topic that stayed provisional (T3, `named_by = rule`; model down, or the 5-per-attempt cap) has `title = short_title(label)`, the first employer's own words. It reaches 16 employers when 16 employers use exactly that `label_norm` (T2). Change R6: "`propose_topics` only proposes a topic whose `named_by` is `model` or `class`. A provisional topic over the threshold gets one naming call at that moment; if it fails it stays `counting`." Add a title/description check: no sighted employer's name (D-210 match), no `?`, at most 60 characters.

**M2. The counter counts topics the profile already has a field for (R3).** R3 excludes "a field whose fact has a profile path (`target_path` set)". `capture_assumptions` always sets `target_path=""` (`apply/questions.py:437-443`), so an assumed answer to a question whose fact has an empty RECOMMENDED field (earliest start, notice period, current salary) is counted and, at 16 employers, proposed as a second field beside the one that exists. Change R4 T4: "The naming call also receives the form's field titles (no values) and may reply `profile_path` (validated against `applicant.form_targets`). Such a topic is `named_by = class`, is never proposed, and its sightings feed `needed_by[path]` ('Needed by {n} applications') instead." Add to R3: "Counted rows are required fields only (`s.required = 1`)": an optional guess is not something an application needs. The query gets that one predicate.

**M3. No full ID, and a sensitive proposal, must not go through "Add to details" (R4 T1, R6, B.10 d2).** T1 makes `owner_fact_national_id` a proposable topic; "Add to details" would then ask for a value that `applicant.validate` refuses (`NRIC_ANYWHERE_RE`, `applicant.py:1082-1089`; PRD:352), a confusing 422 on the Profile page. Change R6: "Topics `owner_fact_national_id` are counted and shown in `apply topics` but are never proposed. `owner_fact_passport` and `owner_fact_bank` are proposed with `sensitive: true` and the form copy 'Stored on this computer only.'" Also say in the proposal copy that D-201 means the local model reads it.

**M4. Validation messages and a deep link must not carry a wording (B.4, B.6).** A section save PUTs the whole profile; `applicant.validate` also validates every `extra` entry (`applicant.py:1140`, `validate_extra`), and a failing entry's error path is `extra.<slug of the employer's wording>.value`, shown by `remapErrors` as "Fix 1" with a "Go to" link. `otherKeys` is safe (`applicantForm.js:179`, `within(path,'extra')` is covered), but errors are not. Change B.4 States: "An error whose path starts `extra.` is never drawn on the Profile page. It becomes one line in the status line: 'A saved answer needs attention. Open Settings → Apply → Answers you corrected.' The save of a section whose own paths are valid still succeeds." (If the server cannot save past an invalid unrelated entry, the section save sends only the section's paths plus the unchanged `extra`, and the server validates `extra` only for entries the request changed.) Pin: a profile with an invalid `extra` entry named after a fixture wording: the Profile DOM holds neither the key nor the message.

**M5. The old-bundle contract is under-specified (B.5, `GET /api/questions`).** The old bundle reads `mode`, `counts`, `busy`, `model_sees_private` as well as `groups`, `ready`, `waiting` (`web/routers/questions.py:316-355`). Change the row to: "`GET /api/questions` returns `{mode, groups: [], counts: {open: 0, assumed: 0, answered: 0, dismissed: 0}, ready: [], waiting: [], busy, model_sees_private, retired: true}` for every `status`." Simpler and safer: also make `POST /questions/answer`, `/dismiss`, `/retry` answer 410 now, not "keep working for one release": nothing can reach them once the list is empty, and a working writer is only surface (it writes `extra` by a key the caller sends).

**M6. "Try them again" is a real submission and must not be a toast action (B.2e, B.4 copy).** With `apply.mode: auto` and no confirmation (D-203), the button sends real applications. A toast auto-dismisses (WCAG 2.2.1 timing) and sits where a mis-click lands. Change: "After Save section with waiting roles, an inline notice inside the saved section (it stays until dismissed): 'Saved. {n} applications were waiting for this.' with the button 'Apply again to {n} applications'. Only roles whose every waited path is now filled are in {n}. The button calls `POST /api/apply` with those job ids; nothing else in the app does." Pin: saving a section issues no `POST /api/apply`; `ready_to_retry` is false for a job with any `submitted` attempt.

### LOW (note for the engineer, no design round)

- L2. Counter employer key: use `COALESCE(NULLIF(employer_norm,''), 'c:'||company_id, 'job:'||job_id)`; a blank `employer_norm` with a known company would otherwise count each job as a new employer.

Post-attempt naming (R4 T4): run it after the browser session is closed and the attempt row is final; skip it when the queue is stopping or paused; stop the pass at the first transport failure (five 15 s timeouts after every attempt would add 75 s of idle queue time when the model is down); name in order of employers descending.

## Answers to the eleven questions

**1. Diagnosis: right.** I traced the claims on `personal`: `_capture_questions`/`capture_page` capture every required unknown (`questions.py:341-394`, `apply_flow.py:1373-1380` raises `unanswerable_required` after `capture`), `page_reason` maps any model "unknown" without a unique tier-2 row to `no_rule` (`questions.py:306-338`), a tier-2 stop is final and tier 5 never runs for a sensitive field (`resolve.py:1700-1716`), `upsert_question` reopens an answered row and inserts `open` (`store.py:2069-2097`), identity is the qualified wording (`plan.py:148-170`, `questions.py` `signature`), and `question_groups` carries company names (`store.py:2226-2288`). The line numbers are accurate to within a few lines. Missing: A.3 never explains the 3 `no_option_fits` (G2d/G2e: the model's pick was not among the options, or no option fits) and the 2 `attestation_unclear` (L3/L7: the declaration reader was unsure) of the 24. They are not `no_rule`, so the "wording did not match" root cause explains only the 18; the other 5 are guard and lock vetoes (C1). The design handles them correctly (B.2d row 4: a protected class with no truthful option ends protectively, not counted) but should say so in A.3 in one line, so the next reader does not look for them in the counter.

**2. Does it meet D-215 literally: yes, once M1, M4, H1 are in.** Places where a wording or a name could still reach the Profile page, after the build: (a) the proposed field's title and description: M1; (b) validation messages naming an `extra` slug: M4; (c) the status line and the "Needs one detail" text: safe, they carry the profile's own field labels (`owner_fact_path`, `store.py:1951-1975`, returns a path only); (d) the badge: `details_needed` is a list of profile paths, no wording; (e) deep links: `#/profile/details` plus a field path, no wording; the old hash for the cards lands on Your details; (f) old bundle against new backend: M5, degrades to an empty list; (g) `strict`: the design says it shows no cards (R1); that is enforced only if no code path renders `questions` rows: pin the Profile DOM under `strict` with open rows from an employer-named fixture (new pin 14). **"Answers you corrected" in Settings is within the spirit.** D-215 is about "this page" and about unbounded growth driven by employers. This list grows only by the owner's own explicit click, one entry per correction, with Forget; the Profile stays free of it. I accept it, but record it as an owner-visible choice (it shows employer names for scoped answers, and a title that came from an employer's wording) and cap the list display at 20 with "Show all". **"What was sent" on the application is the right home** (PRD F-39, principle 5).

**3. Threshold: employers is the right reading; keep it.** The owner's rule is aimed at "specific questions asked by specific companies". Sixteen roles at one company asking "Why Example Co?" are one company's question; the D-204 cap of 10 per employer per day makes crossing 15 by job ids possible in two days. Counting employers is also what "different applications" means in the owner's argument (a question from many different places). Ship `employer` as the default and make it a config value `apply.topics.count_by: employer | job` instead of the "one token" code edit, so the owner's answer to B.10 (1) needs no release. Recognition: T1 (four fixed no-field facts) is sound; T2 (same `label_norm`, any kind) is sound because `label_norm` is the normalised label only for non-generic labels (`plan.py:165-170`), so generic ones ("Please specify | @step#2") never merge across employers; T3/T4 are sound with M1, M2, H1. Your three examples: "Notice period" and "Notice period (days)" are one topic by T2/T4; "How much notice must you give?" probably merges by T4; "When can you start?" is a different question (a date) and should be its own topic; but all three have profile fields (M2), so none should become a proposal; they feed "Needed by {n} applications". A wrong merge can produce an odd proposal (cost: Not needed) and, without H1, a wrong silent answer; with H1 it cannot. The naming call cannot fail the queue as written (it runs after the attempt; L3). **Counter (B.5):** the SQL is correct (DISTINCT employer over `topics ⋈ questions ⋈ question_sightings`, `HAVING > :t`, `UNIQUE (question_id, attempt_id, field_key)` and `INSERT OR IGNORE` make retries count once, `store.py:286-300`); it is cheap (two indexes; thousands of rows) and runs once per attempt end. After a decision: `proposed` -> shown once; `added` -> sightings continue, nothing shows; `dismissed` -> never proposed again (a later merge into it is also silent); `remembered` -> never proposed. One more gap: `upsert_question` on an existing `sig` does not set `topic`, so a row created before Step 2 stays at its backfilled key; the Step 2 migration should end with one capped naming pass over the provisional topics (L3 applies).

**4. What replaces the cards.** (a) Everything the owner needs is there (answer, basis, assumed mark, reason, Not answered, Saved for next time). The remember route is safe only with H2 and H3. Scope is chosen by the owner at the click (default this employer, H3). It cannot override a work-rights or locked-consent truth (held L4/L5 rows win before L6, `locks.py:297-299`), but it could override a standing declaration (H3). (b) Every stop reason has a place: owner-fact with a field and consent: the field path (`attempt_question_paths`); `document_missing`: Files; a fact with no field (passport, bank, ID): the row's own "this form asks for your {fact}" text; ordinary no-basis questions are assumed, not stopped; `validation_error` and the protective ends: the row reason. One gap: `attempt_question_paths` returns the newest path only (`store.py:1951-1975`), so a role missing three facts says "Needs one detail" three times over three retries; acceptable, but the chip could say "Needs {n} details" from the count of path-bearing sightings (no design round). (c) Retry: `canRetry` offers Try again for every ended role with no card check (`attempts.js:224-228`; `POST /api/apply` has none), so the 24-card stopped attempt can be retried the moment the filler is `always`. Triggered only by the owner's click (the row button, or M6's button); the queue starts nothing alone and stays paused after a restart (AQ). Nothing retries by itself.
